= Browser streaming contract
:page-type: architecture
:page-status: current
:summary: The incremental production decoder ABI and bounded-buffering contract for browser streaming.
:nav-order: 40

The production browser API is incremental and container-aware. A whole-file `decode_entire_file`
interface is intentionally not the primary ABI.

[#avl-production-wasm-surface]
== Production WASM surface

The current production WASM surface is conceptually:

[source,text]
----
decoder_create(config) -> handle
decoder_destroy(handle)
input_reserve(handle, len) -> ptr
decoder_push(handle, len)
decoder_pop_video(handle)
decoder_pop_audio(handle)
decoder_seek_reset(handle, ...)
----

`input_reserve` exposes the production parser's own tail storage. JavaScript writes fetched bytes
there and `decoder_push` commits them; validated packet payloads are consumed as borrowed views rather
than copied into a second input packet buffer. Arbitrary transport fragmentation, including one-byte
fragments, is covered by the native parser tests.

The WASM ABI also exposes the Rust-validated front index (stream descriptors and epoch byte ranges),
so the browser does not maintain a second implementation of Avelune file-header/front-index/packet
framing or CRC rules.

[#avl-artifact-selection]
== Artifact selection

The browser loader tries the separately built SIMD128 artifact first and falls back to the scalar
artifact. SIMD support is therefore a module-selection concern rather than pretending native-style
runtime dispatch can make one SIMD-containing WASM binary universally loadable.

Browser threads are not required for baseline correctness and are not part of the current validated
artifact set.

[#avl-range-and-buffering-rule]
== Range and buffering rule

JavaScript remains responsible for HTTP Range scheduling and presentation. It fetches the fixed
header, then the exact validated front-index length, then indexed epoch ranges. The Rust production
container/parser handles interpretation and validation of those bytes.

The player processes one indexed epoch at a time and does not require decoding the entire file before
playback. Reference-picture history remains bounded by the codec's four-reference limit. WebGPU is
currently a presentation/experimental compute path and is not claimed as a validated codec backend.
