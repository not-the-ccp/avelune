[#avl-webgpu-decision]
== Decision

WebGPU is a *supported optional presentation backend* and an *experimental codec-compute backend*.
It is not a conformance dependency. Every Draft Generation 1 stream is decodable and encodable by
Rust/WASM without WebGPU.

Primary references:

* https://www.w3.org/TR/webgpu/ — W3C WebGPU
* https://gpuweb.github.io/gpuweb/ — GPUWeb specification/explainer
* https://www.w3.org/TR/webcodecs/ — W3C WebCodecs

WebGPU exposes compute shaders, storage resources, and explicit command submission. Those are useful
for regular data-parallel image operations; they are a poor fit for moving the codec's serial parser,
entropy state, and reference bookkeeping wholesale onto the GPU.

The browser demo's ordinary-media importer currently uses an embedded FFmpeg WebAssembly build for
foreign container/codec ingest. WebCodecs remains a possible integration path where browser support
and format coverage make it useful.

[#avl-webgpu-hybrid-architecture]
== Hybrid architecture

Bitstream parsing, canonical varints, rANS decoding, immutable-reference bookkeeping, mode decisions,
and container assembly stay in Rust/WASM. Their control flow is serial or irregular, and moving them
to the GPU would add synchronization and staging costs.

Candidate GPU work is coarse and batchable:

* encoder motion-search SAD/SSE grids;
* transforms and inverse transforms;
* distortion metrics for RDO;
* block reconstruction and future local filtering;
* scale/composite/color conversion for editing;
* keeping decoded or source frames GPU-resident through an editor pipeline.

For browser editing, a possible topology is:

[source,text]
----
WebCodecs / canvas / camera / uploaded frames
                   |
                   v
        WebGPU editor + analysis graph
          |                    |
          | bulk costs/blocks  | GPU-resident preview
          v                    v
       Rust/WASM control -> ALV1/ALA1/container
----

WebCodecs does not make a custom codec automatically available through `VideoDecoder` or
`VideoEncoder`; Avelune therefore uses its own WASM decoder.

[#avl-webgpu-compute-prototypes]
== Compute prototypes

`web/webgpu/motion_sad.wgsl` evaluates the full integer-pixel candidate grid for one 8x8 source
block, one workgroup per motion candidate.

`web/webgpu/reconstruct_wht.wgsl` receives entropy-decoded/dequantized coefficients and prediction
samples and performs the normative integer inverse WHT plus clipped reconstruction, one workgroup per
8x8 block.

`web/webgpu/smoke.html` compiles and exercises both kernels, checks zero-motion SAD, and checks a known
inverse-WHT reconstruction.

The prototypes keep rANS and syntax on the CPU side. A production GPU codec path would need to batch
many blocks per submission and avoid CPU readback in the inner loop.

[#avl-webgpu-validation]
== Validation requirements

WebGPU presentation has a Canvas2D fallback and does not affect decoded semantics. Experimental
compute kernels are not considered a validated codec backend until they have CPU/GPU differential
coverage on real WebGPU implementations and hardware.

Any reconstruction work moved to WebGPU must remain bit-exact with the Draft Generation 1 integer
specification. Performance claims should be reported with the tested browser, GPU, driver, workload,
and comparison path rather than inferred from shader compilation alone.
